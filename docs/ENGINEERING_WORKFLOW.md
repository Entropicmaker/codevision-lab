# 工程操作与变更流程

## 1. 目标

本规范保证不同模型、不同会话对同一仓库的修改可复查、可测试、可部署，也避免内容扩展逐渐破坏算法引擎、响应式布局和视觉一致性。

## 2. 开工前检查

```bash
git status --short --branch
git log -5 --oneline
```

- 确认在预期仓库与分支。
- 先读任务相关的类型、注册表、页面、相邻实现和测试。
- 工作树不干净时，区分用户修改与本任务修改；不要 stash、reset 或 checkout 用户修改。
- 依赖目录缺失时用 `npm install`；自动化与可复现环境使用 `npm ci`。

## 3. 计划规则

满足任一条件就先写计划：跨 3 个以上文件、引入/迁移 schema、批量补内容、改变路由/状态、修改部署、预计超过 30 分钟。

计划必须包含：

1. 用户结果：完成后用户能看到或做到什么。
2. 当前证据：相关文件、现状与已知限制。
3. 范围边界：明确不做什么。
4. 实施切片：每个切片可单独验证。
5. 验收标准：命令结果 + 浏览器行为 + 内容准确性。
6. 风险与回滚：最可能破坏的契约，以及如何发现。

模板：`docs/templates/TASK_PLAN.md`。

## 4. 实施顺序

推荐按依赖方向工作：

```text
类型/schema → 引擎或数据 → 注册表 → 页面/UI → 测试 → 文档
```

- 优先扩展现有抽象；只有现有 schema 无法表达需求时才引入新层。
- 新 UI 先查 `src/components/ui/` 是否已有 Button、Badge、Panel、Tabs、Modal、EmptyState。
- 颜色、圆角、阴影、字体、背景从 `global.css` 语义令牌取值。
- 页面路由保持懒加载；Monaco 与 Pyodide 不得进入首页首屏 bundle。
- localStorage schema 变更必须提高 version 并设计 migrate，不能让旧用户数据导致页面崩溃。
- 删除/重命名内容 id 前先检查进度记录、URL、先修关系与注册表引用。

## 5. 响应式与交互标准

| 视口 | 主要要求 |
| --- | --- |
| 320–639px | 单列、无页面横向溢出、主要操作可触达、控制器不遮内容 |
| 640–1023px | 平板双列或折叠布局，代码/图表保持足够空间 |
| 1024–1279px | 避免拥挤三栏；算法页继续用标签/折叠策略 |
| ≥1280px | 完整导航与多面板布局，可视化优先 |

交互硬要求：

- 触控目标至少 44px；装饰元素不能拦截点击。
- 所有功能可通过键盘访问；使用 `:focus-visible`，不可移除焦点而无替代。
- 抽屉/Modal 打开时限制焦点，关闭后恢复到触发控件。
- 状态不能只靠颜色表达；图例或文本必须保留。
- 尊重 `prefers-reduced-motion` 与用户的 reduceMotion 设置。
- 仅组件内部表格/代码区允许横向滚动，body 不允许。

## 6. 性能边界

- 新依赖前先评估是否能用现有代码完成；说明 bundle 与维护成本。
- 路由级页面继续用 React lazy；编辑器只在代码标签真正打开后加载。
- Pyodide 只在 `/lab` 执行 Python 时加载，并继续运行在 Worker。
- 可视化优先 SVG；大量节点超出合理规模时再提出 Canvas 方案，不要在同一任务静默重写渲染层。
- 构建出现大 chunk 警告时先确认是否已按路由/交互懒加载，再决定拆包，不能简单提高阈值掩盖回归。

## 7. 依赖与配置

- 只使用 npm，提交 `package-lock.json` 的同步变化。
- 不手改 lockfile。
- 不做顺手升级；安全或兼容升级应独立任务、独立提交。
- Node 以 GitHub Actions 的 22 为可复现基线；README 声明最低 Node 20。
- Vite 生产 `base` 必须保持 `/codevision-lab/`；开发环境保持 `/`。
- SPA 直达依赖 `scripts/copy-404.mjs` 生成的回退页，构建链不能漏掉。

## 8. Git 操作规范

### 提交前

```bash
git diff --check
git status --short
git diff --stat
```

- 确认没有 `.env`、凭据、构建产物、测试报告或无关文件。
- 按变更范围运行质量矩阵。
- 用 `git diff` 复查生成内容，尤其是批量知识点。

### 提交

推荐格式：

```text
feat: 补充 Python 文件读写知识点
fix: 修正 Dijkstra 边界案例
test: 增加课程注册表内容约束
docs: 添加 DeepSeek 工程交接规范
refactor: 迁移课程双语内容 schema
```

一个提交聚焦一个可说明的结果。不要把依赖升级、视觉重构和批量课程内容塞进同一提交。

### 推送与部署

只有用户明确要求时才 push。`main` 推送后的完成链路是：

```text
build → deploy → production-smoke
```

三个 job 全部成功后，再访问线上关键路由；若失败，先查看失败步骤日志，不要反复空提交重跑。

## 9. 故障处理

- 测试失败：先缩小到单文件/单项目复现，再定位根因；不要用 skip 或放宽断言消除真实失败。
- 类型失败：修类型或数据，不用 `any`、`@ts-ignore` 掩盖。
- E2E 偶发：查看 trace、元素稳定性和异步边界；只有确认环境性问题后才调整等待策略。
- 构建成功但线上失败：重点检查 base path、动态 import、Worker URL、CDN、404 回退和缓存。
- 内容冲突：以语言规范/权威文档和实际可运行结果为依据，记录取舍。

## 10. 完成定义

一项工程任务只有同时满足以下条件才算完成：

- 用户要求对应的行为已实现；
- 相关代码、内容、测试和文档一致；
- 适用验证全部通过；
- 无无关修改和遗留调试代码；
- 已说明已知限制；
- 若要求上传，提交、push、Actions 与生产冒烟均完成。
