# 教学内容编写与审核规范

## 1. 内容目标

CodeVision Lab 的内容不是百科摘录，而是能让学习者完成“理解 → 观察执行 → 修改输入 → 练习 → 验证”的教学单元。每个知识点都应准确、渐进、可运行，并与页面、进度和练习系统连接。

## 2. 通用质量标准

每个新内容必须做到：

- **准确**：术语、版本差异、复杂度、输出、边界行为可验证。
- **聚焦**：一课解决一个核心问题，不堆叠无关高级概念。
- **渐进**：先解释动机与心智模型，再给语法、例子、错误和练习。
- **可运行**：示例完整，输入输出吻合；不留下伪代码冒充真实代码。
- **跨语言诚实**：解释语义差异，不强行说三种语言“完全一样”。
- **双语一致**：所有 `LocalizedText` 的中英文含义一致，不只翻译标题。
- **边界明确**：写清适用前提、空输入、极值、重复值、版本要求或未定义行为。

事实核验优先使用语言官方文档、标准或实际编译/运行结果；算法结论优先教材、论文或严谨推导。无法验证时删去武断结论或在文案中明确限定条件。

## 3. 新增课程知识点

### 3.1 先定位课程骨架

1. 在 `src/content/lessons/chapters.ts` 找到语言、分组和章节 id。
2. 检查是否已有相同主题或可扩展的相邻知识点。
3. id 使用 `<language>-<topic>`，一旦发布不要随意改名，因为 URL 和本地进度会引用它。
4. 先修项必须是已注册的 lesson id，并形成真实可学习顺序。

### 3.2 文件与注册

- 新建 `src/content/lessons/<lesson-id>.ts`，沿用当前文件命名习惯，例如 `python-functions.ts`。
- 导出一个 `LessonMeta`。
- 在 `src/content/lessons/registry.ts` import 并加入 `lessonMetas`。
- 在数组中的顺序就是课程页前后导航顺序，不能只追加到末尾而破坏章节顺序。

### 3.3 LessonMeta 内容要求

| 字段 | 最低要求 |
| --- | --- |
| `title` | 中英文准确、简短 |
| `difficulty` | 根据先修知识和认知负担确定，不按代码长度判断 |
| `prerequisites` | 0–3 个必要先修，均已存在 |
| `concept` | 3–6 段中文；动机、规则、执行模型、边界，避免重复代码注释 |
| `codeExamples` | C++、C#、Python 都提供完整示例；目标语言是主示例，其他语言用于对比 |
| `comparison` | 2–5 个真正有教学意义的语义/语法差异 |
| `commonMistakes` | 至少 2 条；说明为什么错、何时发生、如何修正 |
| `exercise.prompt` | 可独立理解、范围明确、结果可验收；中英文一致 |
| `exercise.hints` | 2–4 条中文递进提示，从思路到局部实现，不直接泄露完整答案 |
| `exercise.answer` | 完整、可运行、覆盖题目要求与关键边界 |

当前 schema 的 `concept`、`hints`、`answer` 不是完整双语结构。英文 UI 会隐藏未翻译课程正文。若任务目标是完整课程英文化，应先单独设计 schema 迁移、兼容旧内容、页面渲染与注册表测试，不能只在组件里继续写临时判断。

### 3.4 示例代码规则

- C++ 以现代、可移植写法为主；涉及标准版本时标注 C++11/17/20 等。
- C# 涉及语言/运行时版本差异时标注版本，避免把特定框架 API 当成语言规则。
- Python 明确版本敏感行为；当前实验室以 Pyodide 支持的 Python 为运行环境。
- 输出注释必须和实际结果一致。
- 代码要完整展示关键路径，不能用注释代替题目核心实现。
- 不为展示简短而引入未解释的高级技巧。

### 3.5 课程验收

- 课程树能看到新知识点，标题、难度、前后导航和先修关系正确。
- 课程详情的概念、三语言切换、对比、错误、提示、答案完整。
- 练习页能筛选并跳到 `#exercise`。
- 标记完成后进度页统计正确。
- 中文界面无缺失字段；英文界面无中文泄漏或误导性的“已完整翻译”表述。

## 4. 新增或修改算法内容

实现契约以 `docs/ALGORITHM_CONTRIBUTING.md` 为准。内容审核额外要求如下。

### 4.1 教学叙事

- 描述先写问题与核心不变量，再写步骤；不要只改写 Wikipedia 定义。
- 复杂度必须与仓库内“实际 Runner/示例实现”一致。例如教学简化版并查集不能宣称具有未实现的路径压缩复杂度。
- 写清前置条件：有序数组、非负权边、连通图、容量范围等。
- `commonMistakes` 至少覆盖一个逻辑错误和一个边界/实现错误。

### 4.2 四份代码行映射

C++、C#、Python、伪代码使用同一组逻辑 id：

```text
C++ / C#：//>compare
Python：   #>compare
伪代码：   //>compare 或 #>compare（以提取器支持为准）
```

使用 `extractLineMap(source)`，不手写行号。Runner 每个 step 的 `codeLineId` 必须在四份代码中存在。

### 4.3 案例设计

至少包含：

- 一个能展示核心过程的默认案例；
- 一个正常 preset；
- 空输入（若允许）；
- 单元素或最小规模；
- 未命中/无解/不可达等失败路径；
- 算法特有边界，如重复值、负权、环、断图、极端窗口大小。

有 aux 参数时，每个案例要明确 `aux`，不能只改名称却仍使用默认值。

### 4.4 Runner 测试

每个 Runner 至少验证：

- 默认与边界结果；
- 同输入两次完全相等；
- 修改某一步不会影响其他步骤；
- 关键 `codeLineId` 被执行；
- 错误输入生成明确 invalid 步骤，而不是抛出未处理异常或伪装成功。

注册表测试用于检查全局不变量，但不能替代算法自身的正确性测试。

## 5. 练习设计

当前练习页直接消费 `lesson.exercise`，所以每新增一课也会新增一道练习。题目应满足：

- 预计 8–15 分钟完成；
- 只依赖当前课及其先修；
- 有明确输入、输出或行为判断；
- 不只要求抄写示例；
- 参考答案可读，必要时说明其他合理方案；
- 不把“完成课程”与“答案一定正确”混为一谈——当前进度是用户主动标记，不是在线判题。

若要做测试用例、自动判题、代码执行评分，应先建立独立 Exercise schema 与安全执行方案，不在 `ExercisesPage.tsx` 继续堆硬编码状态。

## 6. 批量内容工作流

批量补课时按小批次推进，建议每批 3–5 个知识点：

1. 列出本批主题、先修关系与事实来源。
2. 先完成一个代表性知识点并验收格式。
3. 批量生成其余初稿。
4. 逐文件复核输出、版本差异、边界和练习答案。
5. 运行类型检查、单元测试、构建。
6. 浏览器抽查本批每一课；至少完整走通一课的三语言、提示、答案与进度。
7. 单独提交本批，更新路线图的完成数量。

不要一次生成几十个文件后只做编译检查。编译通过不能证明教学事实正确。

## 7. 内容评审记录

发现系统性内容问题时，在 `docs/reviews/` 新建日期化报告：

```text
docs/reviews/content-accuracy-YYYY-MM.md
```

报告包含范围、方法、critical/high/low 问题、修复记录、客观验证和仍未处理项。历史报告不代表新内容自动通过；每次新增内容都要重新验收。
